公共代码库

1.分支管理
基于master分支开发, 新特性开发新建feature分支, 测试通过后合并到master分支

2.版本管理

版本号采用X.Y.Z 三个层级. 含义Major.Minor.Patch
X 表示主版本号, 当API兼容性发生变化, X需要递增, 比如某个SPI接口增加一个方法, 则对应的实现会不兼容
Y 表示次版本号，当增加功能时(不影响 API 的兼容性)，Y 需递增。
Z 表示修订号，当做 Bug 修复时(不影响 API 的兼容性)，Z 需递增。

详细的规则如下：

X, Y, Z 必须为非负整数，且不得包含前导零，必须按数值递增，如 1.9.0 -> 1.10.0 -> 1.11.0
0.Y.Z 的版本号表明软件处于初始开发阶段，意味着 API 可能不稳定；1.0.0 表明版本已有稳定的 API。
当 API 的兼容性变化时，X 必须递增，Y 和 Z 同时设置为 0；当新增功能(不影响 API 的兼容性)或者 API 被标记为 Deprecated 时，Y 必须递增，同时 Z 设置为 0；当进行 bug fix 时，Z 必须递增。
先行版本号(Pre-release)意味该版本不稳定，可能存在兼容性问题，其格式为：X.Y.Z.[a-c][正整数]，如 1.0.0.a1，1.0.0.b99，1.0.0.c1000。
开发版本号常用于 CI-CD，格式为 X.Y.Z.dev[正整数]，如 1.0.1.dev4。
版本号的排序规则为依次比较主版本号、次版本号和修订号的数值，如 1.0.0 < 1.0.1 < 1.1.1 < 2.0.0；对于先行版本号和开发版本号，有：1.0.0.a100 < 1.0.0，2.1.0.dev3 < 2.1.0；当存在字母时，以 ASCII 的排序来比较，如 1.0.0.a1 < 1.0.0.b1。
注意：版本一经发布，不得修改其内容，任何修改必须在新版本发布！

3.SNAPSHOT 与 RELEASE
在版本管理中,0.Y.Z 表示软件处于初始开发期, API不稳定. 除此之外在发行1.0.0版本后添加新特性时也会处于不稳定. 
但是新特性版本需要在很多项目中测试, 为了不用在多个项目中修改版本. SNAPSHOT版本可以解决该问题

一旦通过测试,一定要发布RELEASE版本,线上应用只能依赖RELEASE版本

4.依赖管理
基础库必须很稳定,最好不引入其它依赖, 如果必须引入依赖可以考虑使用shade, 把三方源代码拷贝到项目中
工具库功能越多,三方依赖会越多,建议最大化减少三方依赖, 并且需要解决依赖冲突

5.单元测试
工具库单元测试尤其重要, 工具库被大量使用项目使用, 各种场景下使用, 可能还会有基于工具库的特殊用法. 
有时候很小的改动都会引入bug, 所以必须编写大量的单元测试, 覆盖各种场景

6.兼容性
工具库的生命周期很长,期间加入某个特性, 有更好的实现时, 想移除老的实现. 这点和JDK集合框架很类似 
抽象: 暴露抽象/接口, 将实现使用内部私有类实现, 升级版本时不会有问题
桥接: 适配器模式, 如果已经暴露, 可以将实现桥接到新的实现, 但是不能删除原实现, 需要保持兼容

7.简洁易用
公共库被大量使用, 易于使用非常重要, 使用者接入速度快, 理解难度低, 这样才利于推广

8.模块粒度
一个大而全的公共库会传递很多依赖, 解决办法:
要么不传递依赖, scope为provide, 使用方保证添加依赖, 但这个存在兼容性风险
要么将大而全的库拆分多个模块, 需要分别单独引入依赖, 注意多个模块依赖的公用依赖版本要一致,避免版本冲突
当公共库的依赖和应用的依赖存在冲突,且依赖的api不兼容, 可以修改源码/java模块机制(OSGI, java11, sofa boot)

9.扩展性
工具库需要关注,应用方场景多样化,需要设计类似SPI等扩展机制

10.代码质量
code style, check style, sonar 所有项目都该遵守
