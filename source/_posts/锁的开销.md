## CAS为什么这么快
CAS利用了现代CPU提供的原子更新能力, CAS is special machine-code instruction,计数器例子中,始终在一个循环中,读取,增加,然后原子更新,下面是一段英文解释
A CAS
operation is a special machine-code instruction that allows a word in memory to be conditionally set as an atomic
operation. For the “increment a counter experiment” each thread can spin in a loop reading the counter then try to
atomically set it to its new incremented value. The old and new values are provided as parameters to this instruction. If,
when the operation is executed, the value of the counter matches the supplied expected value, the counter is updated with
the new value. If, on the other hand, the value is not as expected, the CAS operation will fail. It is then up to the thread
attempting to perform the change to retry, re-reading the counter incrementing from that value and so on until the change
succeeds. This CAS approach is significantly more efficient than locks because it does not require a context switch to the
kernel for arbitration. However CAS operations are not free of cost. The processor must lock its instruction pipeline to
ensure atomicity and employ a memory barrier to make the changes visible to other threads. CAS operations are
available in Java by using the java.util.concurrent.Atomic* classes. 

高效的原因大概是没有线程上下文切换,而是不停的重试,所以并发很高的话重试次数很多,直到cpu时间片用完,操作系统调度切换线程
CAS也有开销的,会导致指令管线被锁住,其它核心不能执行指令,而且还引入了 memory barrier, 使当前改变对其它线程可见

## Memory Barriers(内存屏障,内存栅栏)
现代CPU因为性能原因,都是乱序执行指令,乱序加载和存储数据的.处理器只需要保证结果正确就可以了,而不用管程序指令执行顺序.
单线程程序中,乱序执行没有什么问题,但是在多线程程序中,共享变量修改顺序对于每个线程来说是重要的,内存栅栏就是指明一段
代码区域更新内存的顺序是重要的.

当多线程共享数据时，重排序将导致错误的结果。为了在共享变量的情况下依然可以使用指令重排序，产生了内存栅栏来保证程序的正确性。
编译器能够在已编译的代码中添加一些额外的软件栅栏,所以软件内存栅栏式为了方便cpu自己生成硬件栅栏
cpu cache之间需要通信(变量被修改),内存栅栏就是用来生成cache通信消息,解决cpu读取到的是最新的值

栅栏类型:
不同的CPU架构有不同的实现方式，以X86为例：
		
Store Barrier,强制所有在store屏障指令之前的store指令，都在该store屏障指令执行之前被执行，
并把store缓冲区的数据都刷到主存

Load Barrier,强制所有在load屏障指令之后的load指令，都在该load屏障指令执行之后被执行，
并且一直等到load缓冲区被该CPU读完才能执行之后的load指令。

Full Barrier，复合了load和store屏蔽指令。
无论在何种处理器上，这几乎都是最耗时的操作之一（与原子指令差不多，甚至更消耗资源），
所以大部分处理器还会支持更细粒度的屏障指令。
栅栏效果,使读取数据和写数据有顺序了
	
现在CPU速度比内存系统快很多,每次从内存中读取数据都会耗费硬件数百个时钟周期,所以现代CPU引入了Cache.
每个CPU核心都有自己的cache, 所以多线程程序修改共享变量时, 每个cpu核心的Cache之间需要通信,解决并行
修改共享变量的问题?
多线程程序并行执行时,每个cpu core都可以并行修改同一个变量在cache中的数据,有了内存栅栏读取和写出被
同步执行了,比如一个线程写x=1, 另一个线程读取时用loadstrore栅栏,必须等到前一个线程store之后再可以读取
这样就保证读取到了最新的值,这就解决了线程间的可见性问题.也就使用了CPU指令,增加了一些特殊机制,保证每个
cpu core看到最新的数据,这种机制没有使用锁,解决了可见性问题.
http://gee.cs.oswego.edu/dl/jmm/cookbook.html 这篇文章详细介绍了内存栅栏类型
	
	

In the Java memory model the read and write of a volatile field implements the read and write barriers respectively.
读volatile变量每次都是读取主存中的值,不会从本地线程栈中读取,因为读的时候使用loadstore会等store了之后才会load,读取的就是最新的数据
写volatile变量都会写到主存中,使其它线程可见(其实是读的时候等待store完成吧?)

#Cache Line

出现原因:cpu读取内存浪费太多机器周期,效率低,故引入cache
带来问题:cpu并发修改统一内存地址, cpu cahce可能不一致
解决办法:一致性协议,

因为CPU速度比内存快很多,所以使用Cache, 一次性cache数据的大小叫Cache Line,一般是64byte,cache之间通信
也要用到这个大小,Cache Line之间通信需要制定一套通信协议,比如MESI协议,每个Cahce控制器不但知道自己cache
的读写操作,也会监听其它cache的读写操作,所以当多个Core都访问一个变量时,一个core修改了,其它core中cache
状态都为invalid

 每个CPU都有自己的cache,如果所有CPU都共享同一个cache的话,会造成排队修改cache,效率太低了,so any cpu
has own cache,所以缓存一致性问题,是多个cache引起的,并不是多cpu引起的
	
使用多组缓存，但使它们的行为看起来就像只有一组缓存那样。缓存一致性协议就是为了做到这一点而设计的
缓存可以通过snooping总线,窥探其它的cache的读写操作.

缓存本身是独立的，但是内存是共享资源，所有的内存访问都要经过仲裁（arbitrate）：同一个指令周期中，只有一个缓存可以读写内存

MESI以及衍生协议

存在cache0 x=1 发生 cache1 x=2 通知cache0 x无效 这时cache0读取x,导致cache1把x写入内存,cache0再读取

store buffer 和 invalid queue会导致MESI协议失效,所以加上内存栅栏

一般对 MESI 的简单实现都是没有实际价值，这是因为发生写操作往往会带来很长时间的等候：首先需要写的 CPU 需要让别的 CPU 将状态转换到 invalid，收到 response 以后才能进行实际的写，为此硬件专家使用了 store buffer（Sutter 同志也说过，modern CPU 如果没有 store buffer 就不值得买，可见这个 feature 对整体性能的影响是不可忽略的）


store buffer:
core0写一个在core1中的数据,core0让core1处理invalid,然后等待改操作完成再继续执行,效率低了,所以引入
store buffer,core写入到store buffer就不管了,由store buffer来完成到内存的写入操作

invalidate queue:
store buffer一般都很小,对于连续的写操作力不从心,
core修改状态为S的变量时,先要invalid另一个core中变量,等待respone然后再修改,invalidate queue用来存在
invalid指令,然后快速返回让发起invalid的core快速执行接下来的指令


As a result, memory barriers are required. A store barrier will flush the store-buffer (ensuring all writes have entered that CPUs cache). A read barrier will flush the invalidation queue (ensuring all writes by other CPUs become visible to the flushing CPU).

So MESI in practice doesn't quite work - not a problem if you're single threaded, but definitely a problem if not.
